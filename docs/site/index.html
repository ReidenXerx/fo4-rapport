Fallout 4 · Advanced Animation Framework

AAF under the hood

Twenty-one things AAF does that are not written down anywhere — several of which contradict what its API looks like it promises.

Every item was measured against a running game or read out of AAF's own decompiled sources. Nothing here is from a wiki or from memory. Measured on AAF 1.7.4.1, Fallout 4 1.10.163, F4SE 0.6.23, against one real install of roughly 800 plugins — so the counts are of that install and the behaviour is AAF's.

This page exists because the same problems get re-discovered by every mod that drives AAF, and each one costs a night. It is a curated selection from the notes kept while building Rapport, an AAF framework; the full set lives in that repository as docs/aaf-under-the-hood.md, with docs/aaf-api.md for the call shapes.

A negative result is worth as much as a positive one here. Several entries below say this does not work and say how many times it was tried, because the expensive failure is not being wrong — it is being wrong in a way that produces no error, no event and no log line.

The five that will bite you

In the order you will hit them.

FINDING 1

AAF goes permanently deaf after a load, and it is a race

Roughly half of all save loads leave AAF unable to run anything: scenes are accepted, no error comes back, no event arrives, and nothing happens. There is no indication anywhere that something is wrong.

AAF_MainQuestScript.EveryTime_Initialization branches on AAF_UpdaterQuestScript.getSWFPath(). Empty means load the interface (UI.Load); anything else means reboot the one already at this path (ui.Invoke(path + ".reboot")). That variable lives in the save, and the only thing that blanks it is the updater's own initialisation. Both quests register for OnPlayerLoadGame, and Papyrus does not order delivery between them.

Which quest winsResult
updater firstpath blanked → main sees "" → UI.Load → ready
main quest firstreads the stale path → .reboot on a menu instance minted in a previous session, which no longer exists → deaf for the session
The cure, verified 3/3 in game and recovering in about four seconds: call the updater's EveryTime_Initialization() first, then the main quest's. Blanking that path costs nothing when AAF is healthy — it is exactly what AAF writes there itself on every load.

It must also precede any Stop()/Start() of the main quest, or the restart re-enters the same branch and buys nothing. Measured: the quest came back running and AAF stayed deaf.

How it was established. The same SWF path came back byte-identical across four game launches and many loads — root1.instance166.instance165 — where a real UI.Load mints a new instance number every single time. It is baked into the save and re-read forever.
FINDING 2

StartScene stamps the actors busy, and only a finished scene clears it

StartScene is not a request AAF might decline quietly and forget. Its Papyrus half does this before handing the call to AAF's DLL: 

actors[I].AddKeyWord(AAF_ActorBusy)

SetActorLocked does the same with AAF_ActorLocked. Both are ordinary keywords on the actor and both persist in the save, and AAF refuses to animate an actor carrying either one.

So a request that never becomes a scene leaves that NPC flagged busy forever — refused by every AAF mod on the machine, for the rest of the playthrough, with nothing anywhere saying why.

Two things follow for anything driving AAF:

  • Check before asking. AAF:AAF_API exposes Keyword Property AAF_ActorBusy and AAF_ActorLocked, so akActor.HasKeyword(_api.AAF_ActorBusy) is a cheap pre-flight. An actor carrying either is someone else's — or a casualty of an earlier failure.
  • Clean up after a failure. RemoveKeyword and SetActorLocked(actor, false) on every request that does not end in a real scene.

And note the trap in the other direction: locking an actor before calling StartScene is a deadlock rather than a reservation. The flag that tells other mods "this one is taken" tells AAF the same thing.

Measured. One NPC picked by three failed runs in a row stopped being usable by AAF at all, which then looked exactly like AAF ignoring the mod for some other reason. GetAAFStatus() returning 2 is what ruled out the alternatives.
FINDING 3

A Papyrus stack does not come back from an AAF call

Every AAF API function — StartScene, StopScene, ApplyOverlaySet, ApplyMFGSet, all of them — ends in AAF_MainQuestScript.sendEvent, which is one line: 

ui.Invoke("HUDMenu", SWFPath + ".receiver.sendEvent", eventData)

The call delivers: the scene starts, the overlay lands, AAF does exactly what was asked. The stack that made the call does not continue.

RunWhat happenedPolls before it stopped
1poll called BeginRequest → StartScene17, last one at the StartScene poll
2every StartTimer removed; same result—
3request 1 returned early at the busy check and survived; request 2 reached StartScene and did not19, last one at the StartScene poll

Run 3 settles it: the same function, on two consecutive requests. The call that returned before reaching AAF left the poll alive; the call that reached AAF killed it.

Scheduling the next poll first does not fix it, and that attempt is what pinned the mechanism down. If the stuck stack had merely errored, the already-scheduled timer would have fired. It did not — so the stack is alive and stuck, and Papyrus will not start a second OnTimer while the first is still running. One stuck poll is every poll after it. Different handlers do run concurrently; it is re-entering the same handler that queues.

The fix is CallFunctionNoWait. Every AAF call goes onto its own stack and the poll returns immediately, so a stack that never comes back costs one stack rather than the framework. Design around the consequence: one poll gets through at most one AAF call. A drain loop with a budget of eight is a budget of one.
One correction worth keeping, because the first diagnosis was half wrong: it is not ui.Invoke as such. ChangeSetting is also a sendEvent and two of them run inside one function without hanging. StartScene does more — makeActorData is ll_fourplay.AAF_MakeActorData, a native call into another F4SE plugin. Which of the two stalls is still unproven.
FINDING 4

Refusals arrive down OnSceneInit, with 4 arguments instead of 11

There is no separate error event, and nothing about the event name tells you which one you have. A real scene init carries eleven arguments; a refusal carries four — an error level in [0] and the message in [1]. 

[034] Failed to start 'FM' scene because there are no 'FEMALE HUMAN + MALE HUMAN'
      animations. Filters: includeTags (KISSING,MOUTHTOMOUTH,HANDJOB,HANDTOVAGINA,HANDTOPENIS)

Check the argument count before believing an event. Treating a refusal as a start is a tight loop: the caller restarts, asks for the same impossible thing, is refused again. Measured at roughly eight restarts a second, every one logging "scene started".

That example also contains the second half of the lesson. includeTags is an AND — it asks for one animation carrying all of those tags, which nothing is. A list of alternatives has to be offered one at a time.

And the refusal is better evidence than any up-front check. A tag index knows a tag exists somewhere; it cannot know whether an animation exists for this pair, in this furniture, here. AAF answering "no" is the only thing that does.
FINDING 5

AAF never ends a scene that has no tree, and duration is ignored

SceneSettings.duration is handed to AAF's DLL, and AAF's own getDefaultSceneDuration() fills it in when a caller does not — so it looks like the scene length. It is not.

A scene requested with duration = 30.0 was still running three and a half minutes later. OnSceneEnd never arrived, both actors kept their AAF_ActorBusy keywords, and the framework sat on "a scene is already running" until its own watchdog fired.

A tree leaves through its own isExit branch; anything else runs until somebody calls StopScene, and until then both actors stay flagged busy — for the rest of the save. Ending a scene is the caller's job. AAF's own MainQuestScript does it that way when an actor walks out of range: 

AAF_API.StopScene(akObj2 as Actor, -1)    ; -1 is "all of it"

One actor is enough — a scene is one thing, not one per participant — and the proper stop is what produces OnSceneEnd, releases the actors and clears the keywords.

So a caller needs a deadlock breaker, but it must not be a scene length: imposing one takes the ending, because the ending is the last thing to happen. And time the stop from OnSceneInit, not from the request — AAF walks the pair to each other first, measured at 12.5 seconds in an open market.

Two more traps stacked behind this one. StopScene is asynchronous: a stop and a start in the same breath earns "that actor is already part of a currently running scene" — the refusal landed at 01:26:53.758 and the old scene ended at 01:26:54.508, three quarters of a second later. Wait for OnSceneEnd. And a tree's declared time is not wall-clock: one tree declaring 120 s ran 179.9 s in one scene and 226.3 s in another. Two samples, two different multipliers — there is no calibration factor. Treat the declared total as a lower bound.

Staging: there is no tree API, and you cannot move a running scene

Findings 3, 4, 6 and 15 of the full set, which are one story.

The word tree appears nowhere in AAF's entire Papyrus source set. Position trees run in the SWF, so a tree cannot be started, steered or queried through the API.

It is reachable through the position layer instead: a <position> may carry positionTree="...", and positions are what StartScene and ChangePosition take. Naming a position is choosing a tree. That is where the staging lives: 

Play Stage 1 -> Play Stage 2 -> ... -> Play Stage 6 -> Climax -> Finish
Stage 0 -> ... -> Stage 4 -> Orgasm -> Taste It -> Relax -> Finish

On the measured install: 83 trees, 42 ending in an Orgasm branch and 22 in a Climax branch, entered from 85 selectable positions, 64 of which reach a real ending, and 72 of 83 carry strictExiting="true".

FINDING 15 · OPEN

ChangePosition has never once succeeded

26 requests, 26 refusals. Across every stage, every scene, on furniture and off it, inside trees and outside — for tags whose content demonstrably exists.

With tag filters, with a named position id, and with no filters whatsoever. The last of those is what settles it: a call asking for nothing in particular is still refused, so this is not a content problem and no tag list fixes it. AAF answers "there are no FEMALE HUMAN + MALE HUMAN animations" every time, while StartScene matches the same pair happily.

FindMatchingAnimations agrees from the other side: 0 for all 17 tags tried, including PenisToVagina, which 2,320 installed positions carry — while the same query with no filter comes back non-zero.

Refuted as explanations: furniture (refused on NoFurn, outside any tree), the default exclusions (1 of 273 positions carries POSE/UTILITY), and string case.

Until this is settled, treat tag-driven position changes as unproven. Everything that has actually worked came from AAF's own trees running themselves: pick the tree at StartScene and let AAF walk it.
FINDING 4 (full set)

A climax cannot be requested by tag — and that is deliberate

Every standalone climax position is hidden on purpose, because the tree is the intended route. UAP's override file does it with two attributes: 

<defaults ... loadPriority="1" isHidden="true"/>
<position id="BP70 Cowgirl Sequence 5" animation="Null" tags="...,Climax,..."/>

So asking AAF for includeTags(CLIMAX) correctly returns nothing, and overriding that back is fighting another mod's deliberate design for something the tree route already provides.

And this is where an XML census goes wrong. An isHidden="true" on a file's <defaults> element applies to every position in that file. Miss it and a whole pack reads as selectable when none of it is: that produced a confidently wrong count of 48 "visible" climax positions that were all hidden, and the wrong count was then used to contradict AAF, which was right. Any census of AAF's XML must fold <defaults> and must drop animation="Null".

Reading what a scene is

FINDING 16

OnAnimationChange is the stage-advance hook. OnStageEvent is silent.

Established by counting events across three complete scenes. OnStageEvent was registered and fired zero times. The hook whose name promises exactly this does not deliver it, and nothing says so.

OnAnimationChange fires once per tree step, and the count matched the catalogue's stage count for all three trees — 6 events for a 6-stage tree, three times out of three. One scene names them unambiguously: Gay Spooning, 02, 03, 04, Orgasm (loop), Orgasm (loop).

OnAnimationStart fires once per scene, on the entry animation only: 2 Start events against 10 Change events. Anything that forwards only Start freezes on the tree's opening position for the whole rest of the scene.

Both carry the same layout: args[2] the position name, args[3] the tag list. No argument carries a stage number — args[0], [7] and [8] were 0, 0 and False on all 21 animation events — so steps must be counted, not read.

The tag list is the only reliable statement of what a scene is, in AAF's own casing: including its furniture (Desk, Couch, DoubleBed, NoFurn) and its composition (F_M, M_M, F_F — females first; there is no M_F).
FINDING 18

"Reaches an orgasm" is a branch NAME. 27 of 61 have no climax tag at all.

Grade a tree from a branch id containing "climax" / "orgasm" / "finish" and you are reading the author's intent, not a fact. Of 74 selectable entries, 61 grade as reaching an orgasm — and only 34 have a position tagged climax* anywhere in the tree, 32 at the exit position.

rxl_bp70_impregnate_mish_Tree is the proof: branches named Orgasm and Finish, and all eleven positions it can reach carry the same tag list with no climax among them. It ran a complete 226-second scene and never emitted a climax tag. Impregnate Cowgirl and Gay Spooning both did.

Grade from the tags when the answer matters. And note this is the same trap as isExit in the opposite direction: there, two trees named a branch "Stage 4 (No orgasm)" and a substring test read them as reaching one.

Appearance: what AAF can and cannot put on an actor

FINDING 19

An AAF animation almost never carries its own facial expression

mfgSet is the facial layer, and it hangs off <action> and <animation>, not off <position> — a census of position attributes finds zero and is simply looking in the wrong place.

Across the whole installCount
mfgSet definitions11
mfgSet references10
against actions2,240
against animations1,358

Roughly 0.4%. The pack that plays most often here references none. AAF's <morph> / <morphSet> layer is a different thing and is body only — Erection, Penis Adjust, Anus Spread, VaginaPenetrate, NippleLength. Not one facial morph among 1,699 entries.

So a framework is the primary source of faces, not a fallback. The risk runs the other way: a set declared lock="true" holds a morph against anything else that would move it, so on those ~10 animations you would override a face the author chose deliberately.
FINDING 21

AAF can apply an overlay but cannot tint one, and nothing on disk paints a face

The overlay vocabulary, from Data/AAF/common.xsd, is the whole of it:

<xs:complexType name="overlayType">
    <xs:attribute type="xs:byte" name="alpha"/>

template, alpha, isFemale. AAF applies a texture somebody else authored, at an opacity. There is no colour, no tint and no blend parameter — whatever the overlay is meant to look like has to already be in the .dds.

959 templates, 16 installed overlay packsCount
biped slot 3 (body)925
biped slot 4 (left hand)34
head0
matching sweat / blush / perspir0
Slot 0 does not work. Three blush templates on biped slot 0 were built, shipped and watched in game across several scenes: the faces were unchanged. F4EE does not apply a head overlay.

The census predicted it — none of the 959 targets the head, and that is not a coincidence of taste — but a census can only say "nobody does this", never "it cannot be done", so it took one launch to settle. A facial flush needs one of the two routes that do reach a face: the CharGen tint layer, or worn geometry with headpart swaps. Neither is an overlay. Sweat is unaffected; it is slot 3 and works.

One more, cheap to get wrong: an overlayGroup's quantity picks. A group with two templates applies one of them, so a set that must apply both a body texture and a face texture needs two groups of one, not one group of two.
FINDING 20

startEquipmentSet REPLACES AAF's undressing

Attempted, reverted, and recorded so nobody tries it again without knowing the cost. Passing settings.startEquipmentSet to StartScene left both actors fully dressed through a complete sex scene. Naming a start set replaces AAF's automatic undressing rather than adding to it.

And nothing said so. AAF accepted the scene, the tree walked, every step and face was correct, and neither log mentioned equipment at all. This is visible only on screen — the worst shape of failure, because it is invisible to every check a plugin can make about itself.

Where the undressing actually comes from: auto_equipment_on = true in AAF_settings.ini, applying AAF's own unEquip set from action tags. startEquipmentSet is a separate, explicit override of that decision. Two further settings matter if this is ever revisited — protect_custom_equipment stops a start set unequipping items with customEquipment states at all, and legacy_equipment_restore = false means AAF restores from a frozen copy taken at scene start.

Deliberately still unknown: ApplyEquipmentSet(actor, setID) is a runtime call and is additive in principle. It was written and never tested in isolation, so "it also breaks undressing" is not established.

Two toolchain facts learned on the way. Actor.GetEquippedWeapon returns a Weapon and Fallout 4 ships no Weapon.psc, so the held weapon cannot be read from Papyrus at all. And the base game has no GetWornItem, only UnequipItemSlot(int) — so a mod that clears a biped slot itself can never identify what to put back.

Across all 180 deployed AAF XML files: zero definitions exist, in AAF or in any content pack. Omit duration and own removal yourself, in game time, in persistent storage.

Reading AAF's own files yourself

None of this needs guessing at. Two techniques do most of the work, and both are better than a wiki because they cannot be out of date:

  • A compiled script's own debug table lists its functions. Dump it straight out of the .pex — no decompiler needed, and it cannot be wrong about a name. AAF_API.pex yields 56 functions, 40 of them public.
  • The string table tells you what a sender actually sends. Custom event names are mangled at compile time to <declaring script, lowercased>_<Event>, so AAF_API.pex contains the literal aaf:aaf_api_OnSceneInit and the VM matches registrations against that string. Register with the name in the table, not the name in the source.
Why that last one is invisible rather than merely annoying

Compiling against decompiled sources with hand-restored CustomEvent declarations, the mangling does not happen. Proven by compiling both forms and reading the string table back: 

RegisterForCustomEvent(api, "OnSceneInit")             ; emits "OnSceneInit"             -- never matches
RegisterForCustomEvent(api, "aaf:aaf_api_OnSceneInit") ; emits "aaf:aaf_api_OnSceneInit"  -- matches

The restored declarations are enough for the handler to compile, so everything looks right: the script builds, registers, and receives nothing. Ever. There is no error, because RegisterForCustomEvent returns void.

What these notes came from

Rapport is an AAF framework for Fallout 4 1.10.163 — an F4SE plugin plus a minimal Papyrus bridge, giving addons scenes that finish, faces, aftermath that survives a save, and a co-save of who has been with whom. Every finding above was learned while building it, which is why each one is tied to something that broke.

The full, unabridged set is docs/aaf-under-the-hood.md in that repository, with docs/aaf-api.md for the call shapes and argument layouts, and docs/runs/ for the raw logs behind most of it.
